# 11 怎样测软件

测试不是「会写代码的人才做的事」。你只是在回答一个问题：

> 软件实际做的事，和说明书承诺的事，是不是一样？

本课的说明书就是软件里的**用户手册**。手册写的是正确结果。

## 1. 先写下「期望」

动手前默念或写在纸上：

- 我要点哪个按钮？
- 做完以后，我**应该看到什么**？

期望必须具体。不好的期望：「排序应该能用」。好的期望：「按 score 降序后，第一行的分数应是表里最高的那个」。

手册每一步都已经写了期望。你的工作是核对，不是重新发明规则。

## 2. 再看「实际」——至少看三处

很多软件会弹出绿色成功提示。提示只能证明「按钮被点了」，不能证明「数据对了」。

请养成习惯，每次操作后看：

| 看哪里 | 看什么 |
|--------|--------|
| 中间表格 / 图 | 行还在不在、人名对不对、曲线标题变了没有 |
| 底部日志 | 写了删除几行、导入几行？和表格对得上吗？ |
| 左侧列表 / 右侧属性 | 是不是多了一张表？行数是不是变了？ |
| 导出的文件 | 用记事本打开 CSV，第一行是不是列名？ |
| 关掉再打开 | 语言、图、表还在不在？ |

**日志、弹窗、表格三处不一致，本身就是问题。** 不要只信其中一处。

## 3. 不要被「成功」骗到

下面这些都**不能**单独当作通过：

- 弹窗是绿色的
- 没有报错
- 对话框能关掉
- 按钮能点、没有闪退

闪退、报错当然要记。没有报错但结果不对，**更要记**——这种问题用户更容易带到工作里。

## 4. 复现：连做两遍

发现不对时：

1. **文件 → 新建**（这次可以不保存），重新导入同一张 `wiki-demo.csv`。
2. 按同样步骤再做一次。
3. 两遍现象一样 → 可以写缺陷，并写「必现」。
4. 两遍不一样 → 写「有时出现」，把两遍差异写清楚。不要因为不稳定就扔掉。

## 5. 一次只测一件事，也要会「换一个按钮试试」

- 发现「删除缺失值」不对，先记下来，**不要**因此跳过后面所有步骤。
- 同类按钮可以再试一个：例如删除不行时，试试**填充缺失值**。如果填充是对的，说明不是「所有清洗都坏了」。这能帮别人缩小范围，也是测试的加分项。
- 升序对、降序不对，要分开写，不要笼统写「排序有问题」。

## 6. 证据

写问题最好带：

- 操作路径：例如「操作 → 删除缺失值 → 应用」
- 截图：表格（能看到 Bob / Dave 是否还在）、日志最后几行、导出文件的记事本窗口
- 是否必现

截图：Windows 用 **Win + Shift + S** 截一块，粘贴到 Word / 邮件即可。

## 7. 怎样才算「测完了」

不是零问题才算测完。对本课来说：

- [ ] [08 跟做](./08-tutorial.md) 从头到尾点过一遍（中途有问题也继续）
- [ ] [09 清单](./09-test.md) A–F 每条都有钩或叉
- [ ] 不一致的条目写成 [缺陷单](./12-bug-report.md)
- [ ] 建议至少找到 5 处不符（多找有奖励感，这是练习目标）

工作流、填充缺失值、透视表、画图、保存工程，都应能点完、软件不应卡死。若某一步让你完全无法继续（窗口消失、无法导入），停下来把现象和日志发给发放安装包的人。

## 8. 本课不要求你做的事

- 不读源代码、不安装开发工具
- 不测「50 万行会不会卡」（用示例表即可）
- 不测 AI、不打开 `.dapro`
- 不必结束 `python.exe` 去制造崩溃（那是选做，见 09 末尾）
